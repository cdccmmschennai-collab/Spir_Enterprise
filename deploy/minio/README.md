# MinIO source-object lifecycle

The uploaded SPIR workbook a Celery worker extracts from is a *source object*:
`spir-files/batch_uploads/<job_id>_<idx>_<filename>`. It exists only until the
extraction that consumes it finishes. Two mechanisms remove it:

1. **Immediate delete.** `process_file_task` calls `discard_source_object()` as
   soon as the pipeline returns — also on a final failure, a timeout and a
   delivery-cap abort. This is the normal path and it accounts for essentially
   every object.
2. **Nightly stale sweep.** `lifecycle_cleanup` (Celery Beat, 02:00 UTC) deletes
   source objects older than `CLEANUP_UPLOAD_STALE_HOURS` (24) and aborts
   multipart uploads a browser never finished. This catches what a crashed or
   OOM-killed worker left behind.

Neither can work unless the credential the server signs with is allowed to
delete. It was not, which is how ~8 GB of processed uploads accumulated:
production had `MINIO_ACCESS_KEY` set to the *uploader* identity, whose policy
grants `PutObject` only, and every delete failed with `AccessDenied`.

## Two identities

| | server side | browser |
|---|---|---|
| MinIO user | `spir_backend` | `spir_uploader` |
| policy | `spir-backend` | `spir-uploader` |
| used by | API, Celery workers, lifecycle cleanup | presigned part URLs |
| env vars | `MINIO_BACKEND_ACCESS_KEY` / `MINIO_BACKEND_SECRET_KEY` | `MINIO_PRESIGN_ACCESS_KEY` / `MINIO_PRESIGN_SECRET_KEY` |
| `s3:PutObject` | yes | yes |
| `s3:GetObject` | yes | **no** |
| `s3:DeleteObject` | **yes** | **no** |
| `s3:AbortMultipartUpload` | yes | yes |
| `s3:ListMultipartUploadParts` | yes | yes |
| `s3:ListBucket` | yes, `s3:prefix` = `batch_uploads/*` only | **no** |
| scope | `spir-files/batch_uploads/*` | `spir-files/batch_uploads/*` |

Neither policy grants `s3:*`, and neither can touch anything outside
`batch_uploads/`. The browser identity has no `DeleteObject` on purpose: its
key id is in the query string of every presigned URL it signs.

Both policies are scoped to `batch_uploads/` because that is the only area on
MinIO today (`UPLOAD_STORAGE_BACKEND=minio`, `STORAGE_BACKEND=filesystem`).
Moving `extracted_rows/` or `avatars/` onto MinIO means widening
`spir-backend-policy.json` to those prefixes first, or the new area's calls
will be denied.

`s3:ListBucket` is a bucket-level action in the S3 policy model, so it cannot
be written against an object prefix in `Resource`. It is fenced with a
`StringLike` condition on `s3:prefix` instead, which is what the stale sweep
(`list_objects("")` under the area prefix) actually sends. A consequence worth
knowing: `head_bucket` — `MinioObjectStorage.ping()` — sends no prefix and is
therefore denied for this identity. Nothing calls it on the `BATCH_UPLOADS`
area; `/api/health` pings `EXTRACTED_ROWS`, which is on the filesystem.

`spir-backend-policy.json` and `spir-uploader-policy.json` in this directory
are the source of truth for both policies. The local Compose stack inlines the
same JSON in `minio-init`, so a fresh `docker compose up` provisions both users
automatically.

## Provisioning

The local Compose stack does this automatically (`minio-init`). On a host where
MinIO runs in its own Compose project, run `mc` inside that container, with the
policy document copied in and the secret generated by `openssl rand -hex 24`:

```sh
mc admin policy create <alias> spir-backend /path/to/spir-backend-policy.json
mc admin user add      <alias> spir_backend "$NEW_SECRET"
mc admin policy attach <alias> spir-backend --user spir_backend
```

Substitute the bucket name in the `Resource` ARNs first if it is not
`spir-files`. Then put the key id and secret in the backend `.env` as
`MINIO_BACKEND_ACCESS_KEY` / `MINIO_BACKEND_SECRET_KEY` and restart the API,
the workers and Beat.

## Backend configuration

Required in the backend `.env` (production: `/root/Spir_Enterprise/src/.env`).
Values are deployment secrets and are deliberately not recorded anywhere in
this repository.

| variable | meaning |
|---|---|
| `MINIO_ENDPOINT` | server-to-MinIO address |
| `MINIO_BUCKET` | `spir-files` |
| `MINIO_BACKEND_ACCESS_KEY` | `spir_backend` key id — signs every server-side call |
| `MINIO_BACKEND_SECRET_KEY` | its secret |
| `MINIO_PRESIGN_ACCESS_KEY` | `spir_uploader` key id — signs browser URLs |
| `MINIO_PRESIGN_SECRET_KEY` | its secret |
| `MINIO_PUBLIC_ENDPOINT` | browser-reachable MinIO address |
| `UPLOAD_STORAGE_BACKEND` | `minio` |
| `CLEANUP_UPLOAD_STALE_HOURS` | `24` |
| `CLEANUP_DRY_RUN` | `false` once the verification below passes |
| `CLEANUP_QUEUE` | `normal` (default) — see below |

`MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` remain supported as the fallback for
both identities (single-identity deployments). Once
`MINIO_BACKEND_ACCESS_KEY` is set **and** a public endpoint is configured,
`MINIO_PRESIGN_ACCESS_KEY` must also be set: the backend refuses to start the
MinIO storage otherwise, rather than signing browser URLs with a
delete-capable key id.

Credentials that were exposed while diagnosing this should be rotated: create
the new users with fresh secrets, update the `.env`, restart the API/worker,
then `mc admin user remove` the old ones.

## Cleanup scheduling

`lifecycle_cleanup` has no caller to choose a queue for it, so with no route it
goes to Celery's default `celery` queue. The deployed workers consume
`-Q normal,heavy` and `-Q giant`; nothing reads `celery`, so Beat enqueued a
cleanup every night that was never executed. It is now routed explicitly to
`CLEANUP_QUEUE` (default `normal`) in both `task_routes` and the Beat schedule
entry. If a deployment renames its queues, set `CLEANUP_QUEUE` to one a worker
actually consumes.

`CLEANUP_DRY_RUN=true` makes every phase log what it would delete and delete
nothing. Leave it on until the verification steps below pass, then set it to
`false` and restart the worker and Beat.

## Verification

Before switching `CLEANUP_DRY_RUN` off, confirm on the host that the backend
identity carries only `spir-backend`, that the uploader identity has no
`DeleteObject`, that a controlled test object round-trips (upload → extract →
source gone), and that one deliberately aged test object is removed by a manual
`lifecycle_cleanup` run. Scope every test to a throwaway key such as
`batch_uploads/_verify_<timestamp>.bin`; the existing backlog is not part of
this change and must not be deleted while verifying.
